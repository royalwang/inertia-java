# Inertia Java documentation

This directory contains the English public documentation, canonical API examples and a private VitePress toolchain. The current documentation describes `0.1.0-SNAPSHOT`. The documentation is published at [royalwang.github.io/inertia-java](https://royalwang.github.io/inertia-java/).

Start at [Inertia Java](index.md), [run the React example](getting-started/quick-start.md), or [create an independent Spring application](getting-started/first-application.md). The [API guide](api-guide.md) remains the detailed integration reference. ## Build and preview locally

These authoring commands run from a source checkout; private tooling is excluded from Java release payloads. Use Java 21, Python 3 and Node 22.22.2 (minimum 22.12). First run `./mvnw --batch-mode install` from `inertia-java/` to produce the required Javadoc classifiers, then from `inertia-java/docs/`:

```sh
npm ci
npm run docs:check
npm run docs:build
npm run docs:preview -- --host 127.0.0.1
```

The default base is `/inertia-java/`. Open the complete URL printed by preview. `npm run docs:dev` starts the source editor preview. `INERTIA_DOCS_BASE=/another/path/` overrides the base; use the same value for build, preview and smoke. Both leading and trailing slash are required.

The static output is `.vitepress/dist/`. It is an offline/preview artifact, separate from the Java release payload. `public/` contains generated byte-identical Java downloads and versioned Javadoc resources extracted from actual classifiers; edit `examples/*.java`, not those copies. Root README and tooling are excluded from public routes/search. The sidebar includes available catalog pages only; planned entries are not placeholder pages.

## Verify browser and source examples

To use Playwright's paired Chromium:

```sh
npx --no-install playwright install --no-shell chromium
INERTIA_BROWSER_CHANNEL=chromium npm run docs:smoke
```

On Linux, add `--with-deps` when installing Chromium. The local default is installed Google Chrome. Smoke starts an owned preview server, checks all available direct page URLs, local search, keyboard search opening/Escape focus restoration, real clipboard copies in both languages (XML/Java/TSX/YAML/sh), mobile navigation, source-download bytes, all eight Javadoc entries/attribution files, representative method anchors and console errors. It records a unique temporary `summary.json` and screenshots. `INERTIA_DOCS_OUTPUT=/absolute/parent` selects an evidence parent directory.

Canonical Java examples require Java 21, Python 3 and built Java/frontend artifacts. From `inertia-java/`, run `./mvnw install`; from `examples/spring-react/frontend/`, run `npm ci` and `npm run build`. Then return here:

```sh
npm run docs:examples
npm run docs:first-application
```

`docs:examples` packages the release, compiles the two existing API examples unchanged in an isolated external Maven consumer, then runs the first-application acceptance. `docs:first-application` runs that tutorial acceptance separately: it creates another independent POM outside the checkout, builds its frontend and checks actual JavaScript-disabled SSR, JSON, hydration, form validation, one-shot flash, navigation and CSR fallback after stopping its owned renderer. It resolves the locally installed library artifacts. `npm run docs:quick-start` also copies the Git source manifest into a new directory without target/node_modules/dist, rebuilds the full example, and verifies JavaScript-disabled HTML, versioned JSON and the existing browser form/navigation flow. It requires Git and the source checkout. The separate commands support focused reruns; compilation alone is not browser acceptance.

All commands retain bounded child-process ownership and unique evidence directories. Processes/outputs from unrelated development sessions are not selected for cleanup.

## Author a page

Add the page to the [catalog](../../docs/inertia-java/open-source-docs-catalog.json), write its Markdown, and change its status from `planned` to `written`. Include one H1 and frontmatter with `title`, `description`, `version`, repository-relative `sources` and `verification` paths. State prerequisites, working directories, expected behavior, failure feedback and actual limits. Canonical runnable source belongs under `examples/`; use VitePress native `<<< @/examples/...` imports for full listings, as in the first-application tutorial. Do not claim arbitrary copied fences are compiled. Highlighting removes the final newline; clipboard checks compare the rendered text and canonical listings with only that normalization. Download checks retain exact byte identity.

`docs:check` prepares actual Javadoc, runs markdownlint and Markdown-parser-based catalog/link/evidence checks, and checks public type maps, 19 core/Boot configuration fields and 11 timer names. Every generated member anchor is checked during preparation. Missing Maven classifiers fail preparation. All seven libraries with generated API symbols now enforce full doclint and warnings-as-errors; source contracts describe public parameters, ownership and failures. `docs:build` keeps VitePress dead-link checking enabled and generates a catalog-filtered sitemap at the canonical Pages origin with the configured base. The sitemap includes both languages and their alternate links; browser acceptance checks its exact available-page manifest. `docs:smoke` checks rendered behavior under the configured base. Pure prose uses the documentation workflow; executable-example/tool changes also run its Maven/browser job. Java runtime changes retain their separate aggregate gate.

The [open-source documentation plan](../../docs/inertia-java/08-open-source-documentation-plan.md) tracks the full 69-page expansion, reference/operations/community work and complete Chinese translations. All 70 catalog pages now have readable English content: the 69 planned new pages plus the retained API guide. D3 adds deployment, reference, testing, troubleshooting and community. All 70 pages have Chinese translations under `zh/`; English remains canonical. The maintainer has enabled GitHub private vulnerability reporting. Actual release-tag snapshot acceptance remains open. A written page count does not establish those launch requirements.

The manual Pages workflow is restricted to the canonical repository’s main branch, builds/tests the chosen `/inertia-java/` base and deploys a separate static artifact. It requires GitHub Pages configured for Actions and an authenticated maintainer to initiate it; its presence is not deployment evidence.

## Maintain generated Javadoc

The site preparation step reads actual classifiers, copies their HTML/resources/attribution into the generated public tree and records the input hashes. Generated files remain outside Git. If an actual classifier references an absent optional DejaVu font stylesheet, site preparation removes only that import and uses the stylesheet’s existing system-font fallbacks. Generated HTML also receives a data favicon to avoid an implicit missing favicon request. The API manifest records input/output hashes for these site-only transformations; classifier archives themselves remain unchanged. A complete API-enabled site must fail if a required classifier is absent; it must not silently serve an older cached tree as current documentation.

Preparation verifies every generated type page and member anchor. `docs:check` also checks public types against the handwritten owner maps, all 19 core/Boot configuration fields and all 11 timer names. These checks detect index/map drift; they do not prove complete member prose.

All seven libraries with generated API symbols enable full Maven doclint with warnings treated as errors, including missing comments and parameter descriptions. The parent build also defaults to this strict policy. Public source contracts describe purpose, inputs, ownership, results and important failure behavior; record component descriptions also document their generated accessors. Passing doclint establishes structural comment coverage, while source review and executable examples establish the described behavior. The dependency-only starter retains its module guide rather than inventing a Java facade.

## Check external references manually

From this directory after `npm ci`, run `npm run docs:links`. The pinned [Linkinator](https://github.com/JustinBeckwith/linkinator) checks deduplicated HTTP destinations collected from canonical English/Chinese Markdown links and images, this index, the module README and contribution/security files. It does not crawl the linked third-party sites. The manual read-only `inertia-java-docs-links.yml` workflow runs the same command and retains evidence; ordinary prose PRs retain their independent hard internal-link/API/build checks.

The command prints its unique evidence location. `destinations.json` retains each original page/fragment reference, and `http-results.json` records HTTP status/classification. 404/410 fails this manual check. Network/timeouts, server errors or rate limits remain `transient-or-network-unverified`; access/bot restrictions remain `access-or-response-unverified`. Those cases require a later retry or maintainer inspection, and `allExternalHttpVerified` remains false. Do not report them as valid links because collection completed. Requests use a 5s timeout and concurrency 8; the owned worker has the existing bounded process budget.

Documented local/example URLs are not contacted. Canonical GitHub main source URLs are checked for existing local targets and labeled `repository-source-local-only`, so a new unpushed page is not presented as published. The check does not validate remote fragments, semantic freshness, authenticated resources or every generated theme/Javadoc URL. Keep internal links/API anchors as hard checks and review external content when a dependency changes.

The README topic migration checker additionally verifies all 44 original titles/anchors, written topic destinations and the SHA-256 of the exact historical README text. The old text remains engineering history outside public search; current guides and Javadoc own the maintained contracts.

## Record documentation-tool declarations

From this directory after `npm ci`, run `npm run docs:dependencies`, or `npm run docs:dependencies -- /absolute/new-or-empty-evidence-directory`. This uses npm's CycloneDX SBOM command with all dev/optional/peer lock entries, independently of the Java/application frontend inventory. It records the raw SBOM, locked paths, installed package identities, declared terms, unchanged observed license/notice texts and SHA-256, review items and input hashes.

Nested copies can have the same npm `bom-ref`. The collector checks every unique lock path, rejects conflicting declarations and validates the graph using identical coalesced component metadata; the original npm JSON is retained unchanged. Missing optional platform packages remain explicitly unobserved. Missing required installed packages, lock mismatch, undeclared graph edges or escaped license files fail collection.

`success=true` means collection/integrity checks passed; `publicationQualified` remains false. Build tools are not all bundled in the browser. Review the actual static distribution's retained notices separately, along with reciprocal/multiple terms and missing declaration/text entries. Node/npm/Python/JDK/browser/OS licenses are outside this package graph. Keep this separate evidence artifact out of Java release payloads and site source commits. CI and the manual Pages build retain it with their evidence.

## Build and retain documentation versions

The private `versions.json` registry starts with no releases. Its stable version/tag/source-commit/archive-digest mappings are append-only. Java publication excludes the registry and snapshot tooling. The native version selector links to the site root for `next` and `/inertia-java/versions/<version>/` for registered releases; archived source and edit links use the immutable source commit. Existing frozen HTML is not edited to add newer versions.

Use `npm run docs:snapshot -- --tag ACTUAL_TAG --output NEW_DIRECTORY` after fetching real origin tags. The tag must contain a stable Maven version, matching catalog/frontmatter/translated revisions and this tooling. The builder verifies origin identity, exports only tagged Git source, builds matching classifiers and locked site tools, and runs check/build/browser acceptance under the version base. It never rewrites snapshot prose into release prose. When Chromium is selected it installs the tagged Playwright browser. Output is a deterministic static bundle and `registry-entry.json`; creating a real release/tag is outside this command.

The read-only manual `inertia-java-docs-snapshot.yml` produces reviewable artifacts and evidence. Attach the bundle to the corresponding existing GitHub release without replacing an existing asset. Then `npm run docs:register-version -- /absolute/path/registry-entry.json` verifies the real tag and public archive before appending the mapping. Review/commit the registry separately. See the public [release guide](community/releases.md) for commands and boundaries.

After a normal `docs:build`, run `npm run docs:assemble-versions` and `npm run docs:smoke-versions` before Pages upload. Assembly fetches canonical release assets, checks SHA-256, source identity and exact file inventory, rejects links/traversal/oversize content and refuses to overwrite changed version trees. A missing or changed archive fails publication; existing public Pages stays untouched because deployment follows successful build/assembly. The browser check follows each registered root→release→next route and checks immutable source links and mobile width. With zero registered releases its evidence reports zero historical journeys.

Tests use explicitly synthetic metadata and temporary Git/archive fixtures. They do not prove a real release build or public deployment. `docs:check` covers registry immutability, exact tag resolution and archive rejection contracts. CI compares mappings with the PR base or previous push commit. Real-tag reproducibility and public archive availability remain unqualified until an actual release is built and accepted.

## Maintain Chinese translations

The locale menu opens the language home. All 71 canonical articles have reviewed Chinese counterparts; page notices switch to the corresponding article and Chinese navigation/body links retain the locale. Generated Javadoc and upstream resources retain their original language. Chinese search uses standard `Intl.Segmenter` word segmentation through VitePress/MiniSearch’s supported tokenizer option. Both indexing and browser queries use that tokenizer.

Each translated page retains its canonical page ID and path under `zh/`, library version, source/verification evidence and the SHA-256 of the complete English Markdown file. The catalog records the same revision. `docs:check` rejects stale revisions, altered executable fences or canonical code-import directives, missing canonical inline API/configuration tokens, unreviewed/missing translations and Chinese Markdown outside the manifest. Mermaid labels may be translated; shell/XML/Java fences and imported source paths remain identical to the already verified canonical instructions.

When changing English, inspect the actual diff, update the corresponding Chinese prose and review technical meaning before updating both revision fields. A fresh hash alone is not translation review. Translation checks prove provenance/structural contracts; human review owns wording and semantic completeness. Run the strict site build and browser smoke afterward: the latter covers all 70 Chinese routes, both directions of counterpart links, Chinese sidebar/body links and actual rendered heading anchors, Chinese search, canonical downloads and mobile navigation in addition to English acceptance.
